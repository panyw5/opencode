# GPT-Pro Session Refactor Progress

## Implemented In This Stage

- One profile-scoped Session Coordinator owns application authentication. Probe and Driver delegate to it. There is no per-CDP authentication cache or local retry loop.
- Authentication requests are single-flight per profile; evidence includes profile generation, page epoch, document epoch and source URL. Cookie-family revocation invalidates evidence without fetching; ordinary website Cookie rotation is not conflated with a new login. Invalid/verification states stop implicit retries; transient failures use shared backoff and Retry-After without background timers.
- Runtime IPC is a cached snapshot. Settings consumes a versioned runtime subscription instead of its former 3-second polling loop. History remains on the existing shared execution-state feed and is not duplicated in runtime events.
- Runtime and Probe status are pure canonical snapshots; the old authentication projection and duplicate history payload are removed. Expensive diagnostics require the explicit inspect command. Authentication metadata never extracts answers or installs answer observers. Document reload increments a separate document epoch, including same-URL reloads; navigation reasons distinguish user, agent, automation, candidate opening and website navigation. Trusted send commits reject a changed document.
- Import now installs into an isolated in-memory candidate jar. Its document-loading barrier and Session Coordinator must verify authentication before encrypted persistence, account-bound execution migration and active-profile promotion. Old jars/pages are never replaced or reloaded. A failed candidate can be explicitly verified again on the same page after human login/verification; Retry-After still applies. Retained generations are bounded to four and are released only after their pages close.
- Managed, unsent consultations can migrate to the verified same-account profile while their old pages/drafts remain untouched. Staged attachments return to pending with their integrity metadata preserved. The job remains paused until explicit resume, which revalidates staged bytes and freshly verifies the account before its single trusted send. Attempted/confirmed sends never use this path.
- Secure credential status distinguishes restoration, availability and storage faults. Explicit reconnect can retry initialization/persistence. Restoring an expired/incomplete Cookie family drops the entire observed family rather than restoring selected chunks.
- Profile-local SQLite commits small execution authority and notification outboxes synchronously. Production bodies use independent per-job atomic files with asynchronous write/fsync/rename checkpoints, without taking the critical SQLite write lock. Only dirty bodies are staged; final completion waits for its checkpoint before publishing metadata/notifications. Cancellation/disposal during flush wins. Shutdown, relaunch and signals await GPT persistence before stopping backends. Legacy execution history is imported once and retained read-only; configuration has its own small store.
- Execution metadata write faults revoke the execution feed's authority, suspend dispatch/notification acknowledgement, and release runner locks without automatic retry loops. Explicit storage recovery waits for runners/checkpoints, persists a paused or uncertain authoritative snapshot, and never sends automatically. Healthy recovery is a no-op to execution state. Settings exposes the recovery command only for a storage fault.
- Body flush captures a finite batch so other continuously updating streams cannot starve final completion. The controller re-reads the owned question and answer after the final checkpoint; document/ownership changes fail safely, while changed answer text/HTML is checkpointed again before any completed notification.
- Answer HTML computation is incremental by observed top-level blocks, not merely incremental transport. Only changed blocks are cloned/sanitized; the cache has byte/node bounds and removals release entries. Exact rendered text is still re-read to preserve whitespace/layout semantics. Routine driver metadata reads no answer bodies and avoids cloning old prompt bodies. Security, ownership, rewrite and forced-refresh tests remain active.
- Recovery uses explicit humanAction values for login, browser verification, secure-storage recovery and original-account restoration. Tool results and sidecar notifications use one instruction generator; legacy boolean history/outboxes migrate once. Local connection-token expiry has its own login_connection_expired code, distinct from website login_expired. Neither token expiry nor a Pro label is used as authentication evidence.
- Credential initialization readiness is explicitly retryable/coalesced. Failed startup Cookie writes roll back the complete previous memory snapshot; secure-storage recovery does not rerun successful initialization. Retired-profile cleanup failures preserve the generation cap and can be retried.

## Current Test Suite

From the repository root, run `bun run --cwd packages/desktop test:gpt-pro`. The runner changes into each package before launching Bun, preserving package preloads and isolating module mocks. `--list` prints the exact files. New `gpt-pro` and `gpt_pro` test files in the configured source/test/script roots are discovered automatically; cross-cutting browser and composer tests are listed explicitly.

| Layer | Responsibility |
| --- | --- |
| util | Error/action contracts, legacy recovery migration, compact execution state and shared store |
| desktop | Authentication transport, profile coordinator and document evidence, candidate import, staged recovery, critical execution commits, asynchronous body journal, crash recovery and notification outbox |
| app | Metadata/owned DOM capture, composer/attachment boundaries, all canonical authentication phases and orthogonal runtime cards |
| ui | Error guidance, read-only historical cards, result rendering, handoff and shared-state behavior |
| opencode | Actual tool adapter, human-action handoff, durable sidecar inbox, descendant-read and browser-command authorization; a separate filtered routing group covers direct mentions, attachment forwarding, denied permissions and progress/completion wakeups in prompt.test.ts |

Modes are mutually exclusive. The default never runs a live website consultation or opens an Electron app:

- `--unit`: six isolated groups in five packages, including the previously omitted tool, read-owner, prompt-routing and CDP-helper tests. The routing group's explicit name filter is printed by `--list`; it does not run unrelated session cases.
- `--baseline`: synthetic old full-history persistence versus the current asynchronous per-job body journal; awaits flush before recording body metrics. Timing is evidence, not a hard CI performance threshold.
- `--native`: a separate temporary Electron process, synthetic Cookie jars, OS encryption, offline synthetic pages, staged text/PNG recovery and same-machine formula/concurrency measurements. It never imports user credentials.
- `--logged-out`: requires an already running development app on CDP 9222. Sends one isolated sidecar message, checks the received human-login notification, asserts zero website submissions and bounds a controlled navigation loop. It refuses an authenticated profile.
- `--live`: authorized development login is mandatory before creating sidecar sessions. Checks one generated-marker question/reply, account/profile binding, single-send evidence, completed notification and parent read-only handoff.
- `--live-rich`: the same isolated route with a generated long Fourier-series fixture; also requires substantive text, rendered math, a table and code. It never loads an original user research prompt.
- `--live-multipage`: generated isolated questions on distinct pages bound to the authenticated profile (including generated profiles), overlapping runners, reply ownership and notifications. Direct script watch mode only observes its saved binding; it never redispatches.

Live completion is checked against the immutable account/profile and submitted user turn, not a requirement that authentication evidence from a replaced pre-send document remain valid forever. Admission and completion authentication states are recorded separately. A Pro label, available encrypted Cookies or a local connection token does not authorize live admission. No mode logs in automatically, relaxes approvals, switches the user's model, clears a manual draft or replays an original consultation.

The legacy `gpt-pro-e2e.ts` is now only a compatibility entry to the isolated marker test. Its original-session prompt extraction, draft-clearing and diagnostic-page mutation flags reject before CDP. Specialized attachment/layout/lifecycle scripts remain explicit diagnostics, not part of the default live-free regression count. Attachment acceptance uses the saved account/profile binding; lifecycle checks use the recorded pageID rather than reconstructing one.
